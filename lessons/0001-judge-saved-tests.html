Lesson 01 · Five minutes · Saved-data tests

Judge a test by the bug it catches.

Your win: explain one strength and one limit of app/lib/saved.server.test.ts using specific assertions.

1. Separate workflow from evidence

Kent Beck’s Canon TDD works through one runnable scenario at a time: write a test, observe the intended failure, implement the behavior, then optionally refactor. The finished test file can show useful checks; it cannot prove that sequence happened.

The local TDD skill places refactoring in the review stage. Beck includes it in the cycle. That is a local workflow convention, not a universal definition of TDD.

For test quality, ask whether the test observes a meaningful result through a public interface and can survive changes to internal code. See Google’s concrete example.

2. Worked example: a rejected edit

saveNote(db, userId, lessonId, "a".repeat(2000), NOW);
expect(() =>
  saveNote(db, userId, lessonId, "b".repeat(2001), LATER)
).toThrow("2,000 characters or fewer");
expect(getLessonSaved(db, userId, lessonId).note?.body)
  .toBe("a".repeat(2000));

This excerpt abbreviates fixture names. The test checks both rejection at the boundary and preservation of the previous Note. An implementation that deletes the old Note before validating the replacement would throw as expected but fail the final assertion. That final check earns its place.

The repeated string is a fixed input and expected preserved value, not a recomputation of the validation algorithm. The test uses actual migrated SQLite via createTestDb; it does not mock Drizzle calls.

3. Your turn: inspect the refund claim

The final test approves a Refund Request, then runs:

expect(listSaved(db, userId, [])).toEqual({
  savedBookmarks: [], savedNotes: []
});
const restored = listSaved(db, userId, [courseId]);

Imagine approval returns success but accidentally leaves the Enrollment active. Would these assertions detect that bug? Explain before opening the feedback.

Reveal feedback

No. The test supplies the access lists itself. It establishes that saved rows survive approval and are returned when the caller authorizes the Course. It does not establish that approval removes content access, or that renewed access is calculated correctly. A scenario exercising the real access decision could establish that separate claim.

This is a limit of the test’s boundary, not proof that production access is broken or that the wider suite lacks coverage.

4. Transfer: does this detect lesson leakage?

The whitespace test saves one user’s Note and another user’s Note on the same Lesson. It clears the first user’s Note and checks the second remains. Imagine deletion filters by user but accidentally omits the Lesson ID. Would this setup catch it?

Reveal feedback

No. That user has only one Note. A second Note for the same user on another Lesson would distinguish the implementations: it should survive clearing the first. This is a candidate scenario to discuss against the feature requirements, not a test we have added.

5. Make your review concrete

Complete these from memory: “I trust this test to catch ___ because ___.” Then: “I would not use this test as evidence of ___ because ___.”

A reasonable initial judgment

The seven tests provide useful module-level integration coverage: toggling, Note updates, timestamps, length validation, owner isolation in selected scenarios, ordering, allowlist filtering, and retention after approval. They mostly assert outcomes via exported functions. Direct fixture inserts arrange data rather than verify the result through raw SQL.

Useful review questions include same-user cross-Lesson isolation, selective filtering with both accessible and inaccessible real Courses, and real access calculation after approval. The “without duplicates” title does not demonstrate concurrent toggle safety; the plain-text body assertion does not establish safe browser rendering.

All seven tests passed in this session. That establishes current execution success, not completeness. These possible faults were reasoned through, not injected and run.
