One structure, represented in two places

Your question gets at the key tradeoff: schema.ts describes tables that SQLite also describes internally. Why keep both? By the end, you should be able to explain what this duplication buys you—and predict when the two can disagree.

1. The database has its own schema

data.db contains persisted rows and SQLite’s own definitions of tables, columns, indexes, and constraints. SQLite uses those definitions to run queries and enforce rules. It does not read TypeScript.

app/db/schema.ts constructs JavaScript objects describing tables and columns, with TypeScript information attached through Drizzle’s types. It contains no saved note rows. Importing it does not create those tables in SQLite. It supplies a description that other code can use. Drizzle schema declarations.

Distinction: the database schema determines what the database currently accepts. The TypeScript schema tells your application and migration tooling what structure you intend to work with. They agree when you keep them synchronized.

2. The description serves two separate paths

CHANGING THE DATABASE STRUCTURE
schema.ts + previous migration snapshot
        ↓ Drizzle Kit: generate
SQL migration files in drizzle/
        ↓ Drizzle Kit: migrate
SQLite changes its tables and constraints

RUNNING THE APPLICATION
schema.ts table objects + application query
        ↓ Drizzle ORM builds SQL and parameters
better-sqlite3 driver executes the statement
        ↓ SQLite reads/writes data and enforces constraints
Drizzle maps results to application properties

In this repo, drizzle.config.ts points Kit at app/db/schema.ts, the drizzle/ output directory, and data.db. The scripts npm run db:generate and npm run db:migrate perform the first path. These are explanations, not steps to run for this lesson.

generate compares schema descriptions with the previous migration snapshot; it does not automatically inspect and repair the live database. migrate applies pending migration files. Generate · Migrate.

3. Follow one query across the boundary

This is the same lookup pattern used in app/lib/saved.server.ts, narrowed to one selected field:

const note = db
  .select({ body: notes.body })
  .from(notes)
  .where(and(
    eq(notes.userId, userId),
    eq(notes.lessonId, lessonId)
  ))
  .get();

Drizzle builds SQL equivalent to:

SELECT body FROM notes
WHERE user_id = ? AND lesson_id = ?;
-- parameters: [userId, lessonId]

From the schema objects, Drizzle knows that notes.userId means the SQL column user_id. It builds the SQL, binds values as parameters through the driver, and infers the selected result shape for TypeScript. A mistyped property such as notes.userID is caught by TypeScript. SQLite still does the actual searching and constraint enforcement. Schema-to-query examples.

The connection glue lives in app/db/index.ts: new Database("data.db") opens SQLite through the driver; drizzle(getSqlite(), { schema }) wraps that connection. This initialization does not run migrations or verify that every declared column exists.

4. What substantial work is hidden?

Your “deep module” intuition is useful: a small query interface coordinates several jobs. Here is where the work lands in this project.

ComponentWork it handles
Drizzle ORMSQL construction, parameter handling, property/column mapping, inferred TypeScript types, and runtime defaults such as $defaultFn.
Drizzle KitSchema comparison, migration SQL generation, and applying migrations.
better-sqlite3 + SQLiteConnection and statement execution; SQLite stores rows, chooses query plans, and enforces installed constraints.
Your applicationAuthorization and business behavior, such as trimming notes and limiting their length.

For example, $defaultFn(() => new Date().toISOString()) is work performed by the ORM at insertion time. The unique user–lesson index becomes work enforced by SQLite after its migration is applied. One declaration file can describe behavior for different layers. Runtime defaults.

5. Could you remove schema.ts?

Yes, if you changed the application’s database approach. A raw SQL version could use the existing driver directly:

const note = connection.prepare(
  "SELECT body FROM notes WHERE user_id = ? AND lesson_id = ?"
).get(userId, lessonId);

You would still need to define and evolve the database tables, perhaps with handwritten SQL migrations. You would also need another way to describe or check result types. Parameterized SQL remains available without an ORM.

Why choose Drizzle here? One TypeScript description feeds query typing, name mapping, and migration generation. Why choose raw SQL? Direct control and fewer abstractions may matter more to your team than inferred query types. Either approach requires keeping application assumptions aligned with the deployed database.

6. Predict the failure

You add a new column to schema.ts, then immediately query it without applying a database change. What happens?

Reveal feedback

TypeScript can accept the new property, but SQLite will report a missing column when the query executes against an unchanged table. The code description changed; the database did not.

You create a table directly in SQLite. Does an exported TypeScript table object automatically appear in schema.ts?

Reveal feedback

No. The database and source file are separate artifacts. You must update the code description yourself or deliberately use an introspection workflow. Drizzle documents both code-first and database-first workflows.
