# Cadence notification service alternatives

Researched 2026-11-10 for [Compare notification service alternatives for Cadence](https://github.com/marcplatt/softwareFact1/issues/10), informing [Choose notification services and establish implementation readiness](https://github.com/marcplatt/softwareFact1/issues/6). Planning only: no provider selection, account creation, credential inspection or app changes. Raze Dev Studios will own accounts. Published prices below are USD monthly list prices observed today; reconfirm before purchasing.

## Product baseline and recommendation

Authoritative requirements: [recipient policy](https://github.com/marcplatt/softwareFact1/issues/2#issuecomment-6775609477), [inbox policy](https://github.com/marcplatt/softwareFact1/issues/5#issuecomment-6775836877), [category/interruption policy](https://github.com/marcplatt/softwareFact1/issues/4#issuecomment-6775852039). Each qualifying event retains an individual inbox entry with independent read/archive state. Category Popup/Push preferences never suppress history. First interruption is immediate, then subsequent activity groups over five minutes; show popups when visible and opted-in push otherwise. Deadline changes/completion/Enrollment require cancellation or eligibility rechecking. Email, SMS and native apps are outside scope.

**Conditional recommendation:** shortlist Knock and Novu Cloud. Knock has the closest explicitly documented leading-item batching primitive and mature headless inbox support. Novu deserves evaluation where lower paid entry cost, US/EU hosting or code-first workflows matter. MagicBell is credible for inbox/web push, with more proof needed for exact grouping and scheduling. Choose application-owned delivery only if the team accepts operating its inbox, realtime, queues, scheduling and token lifecycle. These are engineering judgments, not a provider selection.

Before committing establish volume/fanout, budget, inbox retention, residency, target devices, multi-device/catch-up guarantees, account/credential custody, and failure ownership. No expected traffic is assumed and no free-tier fit is asserted.

## Exact-policy gaps and reliability

**Preserve history:** create individual inbox entries before/separately from grouping. Do not implement Popup off by disabling an in-app delivery channel: that can suppress history. Popup eligibility belongs in the interruption rendering/orchestration branch; Push eligibility is separate. This is an architectural inference from Cadence policy, not verified default-widget behavior. Novu explicitly exposes an in-app channel preference that must be adapted. [Novu channel preferences](https://docs.novu.co/framework/typescript/workflow).

**Knock batching:** its leading-item mode immediately continues the first item, excludes it from the later batch, and produces no later execution if there is no second item. A five-minute fixed window plus recipient/subject key matches the grouping primitive. Keeping individual feed entries while emitting grouped foreground popups still needs an integration design; the default feed toast listener is not proven to do this automatically. [Knock batching](https://docs.knock.app/designing-workflows/batch-function).

**Presence:** websocket connected, unread and document visible are distinct facts. None of the reviewed docs proves Cadence's exact account-wide visibility/multi-device contract out of the box. An explicit expiring presence mechanism or verified provider equivalent is needed. Browser foreground/background handling alone does not atomically decide server delivery. [FCM foreground/background behavior](https://firebase.google.com/docs/cloud-messaging/web/receive-messages). Settle races and catch-up semantics in the delivery-guarantees decision.

**Durability/deduplication:** all options still require a durable Cadence event/outbox boundary, stable event/recipient keys and observable recovery; managed workflows cannot atomically commit with Cadence's domain database transaction (engineering recommendation). Knock defaults to 24-hour API idempotency. Novu transaction IDs prevent duplicate triggers with retention dependent on billing tier and can cancel pending/active workflows. Neither removes durable app deduplication. [Knock API](https://docs.knock.app/api-reference/overview/bulk-endpoints), [Novu official SDK](https://github.com/novuhq/novu-csharp/blob/main/docs/sdks/novu/README.md).

**Retries:** Novu's current policy says provider rejection, including provider 429, fails the step; no automatic provider failover or inspectable dead-letter queue. Failure events/activity logs support app recovery. Infrastructure retries differ from provider-send retries. Exact Knock/MagicBell exhaustion/re-drive policies remain unverified here. FCM acceptance is not proof of device delivery. [Novu retry policy](https://docs.novu.co/platform/developer/delivery-retries), [FCM lifespan](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan).

**Scheduling horizons:** Novu dedicated limits page gives delay limits Free 1 day, Pro 7 days, Team 30 days, custom Enterprise. A reminder created long before a deadline can exceed these. Some pricing-table window entries differ: confirm the purchased plan's contract. An app scheduler avoids this dependency. Regardless of vendor, recheck completion, Enrollment and deadline version before dispatch; a cancellation race cannot retract a push already handed to transport. [Novu limits](https://docs.novu.co/platform/developer/limits), [Knock schedules](https://docs.knock.app/concepts/schedules).

## Privacy, integration, local development and portability

Cadence must authorize recipients server-side, exclude actors/duplicates, enforce Enrollment/private-help boundaries and reauthorize click destinations for every option. Send minimal previews and avoid private conversation content in lock-screen payloads. Bind client identity to the authenticated session and keep API secrets server-side. Novu documents subscriber authentication for production; MagicBell's current JS client uses user access tokens. [Novu production guide](https://docs.novu.co/platform/inbox/prepare-for-production), [MagicBell client authentication](https://www.magicbell.com/docs/libraries/magicbell-js).

Retention/deletion, DPA, residency and account roles need confirmation. Novu advertises US/EU regions. Knock's plans page says EU residency is expected by end 2026: this is not confirmation it is available today. [Novu pricing](https://www.novu.co/pricing/), [Knock plans](https://docs.knock.app/manage-your-account/knock-plans).

React/headless APIs make all three managed vendors plausible in React Router, an inference rather than a tested drop-in integration. Initialize browser listeners after hydration; issue user credentials in authenticated server routes; dispatch in workers. Cadence still implements accessible compact inbox placement and eight-second popup behavior. Local development needs isolated environments/projects, synthetic identities and secure secret handling; browser push needs an appropriate secure origin and real-device testing. No SDK was installed or tested for this research.

For portability, retain domain event IDs, recipient IDs, categories, preferences and schedule versions in app-owned records and isolate transport adapters. Explicitly decide whether hosted history is canonical and how read/archive states migrate. Open-source SDKs do not make hosted data automatically portable. Novu currently lists enterprise self-hosting; verify repository license and feature parity rather than assume free cloud-equivalent hosting. [Novu hosting/pricing](https://www.novu.co/pricing/).

## Browser/mobile limitations

Classic Web Push needs permission, service workers and browser/platform delivery services. WebKit documents iOS/iPadOS 16.4+ push for Home Screen web apps with permission requested after direct user interaction; Focus controls apply. Normal browser tabs are not a universal substitute for that installation flow. Newer Declarative Web Push does not establish support across all target browsers. Sound, vibration and timing cannot be guaranteed by an orchestrator. Test denied/revoked consent, iPhone installation, Android, logout/token cleanup and multiple devices. [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [FCM receiving](https://firebase.google.com/docs/cloud-messaging/web/receive-messages), [MagicBell token lifecycle](https://www.magicbell.com/docs/channels).

## Remaining proof before selecting

Unverified: actual accounts/credentials; traffic; exact Knock/MagicBell retry and re-drive guarantees; MagicBell deadline/grouping semantics; all vendors' precise multi-device visibility and data-export fidelity. Confirm retention/privacy/delivery policy before purchasing. Suggested focused evaluation: Popup/Push off still yields history; three events yield three entries and immediate-first/grouped-rest interruptions; visible/hidden transitions avoid intentional double-alerts; deadline change/completion suppresses stale work; session spoofing cannot access another inbox; outage/retry cannot duplicate history. These are readiness checks, not implementation authorization.
